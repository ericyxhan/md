# MD Service Implementation Plan

SQLite + FastAPI control plane with a separate OpenMM GPU worker.

This document is the handoff plan for the backend implementation. It assumes the
existing simulation workflow (`simulate.py`, `stages.py`, `config.py`,
`parameterization.py`, `output_bundle.py`) is the execution engine and must not
be rewritten into the API process.

## 1. Scope

Build a service that lets a frontend:

- upload protein/ligand inputs or request a PDB ID;
- create an MD job with a configurable number of equilibration stages,
  optional production, integrator/barostat settings, and retry settings;
- monitor job state, stage state, and live progress;
- cancel a job gracefully, preserving checkpoints;
- retry a failed/canceled job by resuming, restarting a stage, restarting all
  stages, or reparameterizing;
- download logs, structures, states, trajectories, checkpoints, and metadata.

The service consists of:

1. **API / control plane** — FastAPI, SQLite, file management, job state,
   validation, auth, and artifact metadata. It never imports OpenMM and never
   creates a GPU context.
2. **Worker / execution plane** — a separate container with the OpenMM image.
   It claims one job at a time, runs `simulate.py` as a subprocess, reports
   progress to the API, and handles cancellation.
3. **Shared job filesystem** — uploads and job workspaces on a persistent local
   disk. SQLite lives on a separate persistent local path.

For v1, API and worker run on the same host with Docker Compose. The design
allows moving to Postgres and object storage later without changing the job
model or the simulation workflow.

## 2. Locked Decisions

- The CLI workflow remains the execution engine. The service wraps it.
- API and worker are separate containers. Do not run OpenMM in the API process.
- The API is the only SQLite writer. Workers report state through internal API
  endpoints instead of opening the database.
- SQLite is used for v1 because the expected deployment is one API process, one
  host, and one GPU worker.
- SQLite is a file on a persistent local filesystem. Use a host bind mount, not
  the container writable layer and not a network filesystem.
- Use WAL mode, `foreign_keys = ON`, `busy_timeout`, short write transactions,
  and exactly one API process.
- Do not expose raw TOML, arbitrary paths, arbitrary executables, arbitrary
  force fields, or OpenMM platform properties to users.
- Stage names are generated by the API. Users may provide display labels, but
  generated names are used in paths and restart requests.
- The worker runs one job at a time per GPU. Multiple GPU workers may be added
  later; the queue is designed for that.
- The frontend is out of scope here. The API must publish a clean OpenAPI
  contract that a frontend can consume.
- Trajectory visualization is out of scope for v1. Artifacts are downloadable.
- v1 is single-tenant or small trusted team. A static API token is sufficient
  initially; OIDC can replace it later.

## 4. Architecture

```text
Frontend / browser
        |
        | HTTPS, bearer token
        v
+-----------------------------+
| FastAPI API container        |
| - auth, validation          |
| - SQLite (sole writer)       |
| - uploads, job workspaces   |
| - internal worker endpoints  |
+--------------+--------------+
               | shared /data volume
               | (bind mount)
+--------------v--------------+
| Worker container             |
| - OpenMM image               |
| - claims one job             |
| - runs simulate.py           |
| - reports progress/status    |
| - handles SIGINT cancel      |
+--------------+--------------+
               |
        GPU / CUDA
```

Request flow:

1. Client uploads input files.
2. Client creates a job.
3. API validates the request, creates the workspace, generates `config.toml`,
   inserts the job and stage rows, and queues it.
4. Worker claims the job through an internal API endpoint.
5. Worker runs `simulate.py` with the generated config and a fixed progress
   file path.
6. Worker sends progress, stage transitions, and final status to the API.
7. API updates SQLite and serves status/artifact/log endpoints.
8. On cancel, API sets a flag; worker sends SIGINT to the process group and
   reports canceled.

The API is the source of truth for job state. Stage manifests and checkpoints
on disk are the source of truth for resumability.

### 6.7 SQLite Connection Settings

Set these on every connection:

```text
PRAGMA journal_mode = WAL;
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 5000;
PRAGMA synchronous = NORMAL;
```

Use a short-lived session per request. Keep write transactions short; never hold
one while hashing an upload, copying a large file, or waiting on a subprocess.
Use `BEGIN IMMEDIATE` for claim/cancel/retry transitions so two concurrent
worker claims cannot both select the same queued job. Retry `database is
locked` a small number of times with a short backoff.

Run exactly one API process:

```text
uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 1
```

Do not use multiple Uvicorn workers with SQLite.

### 6.8 Migrations

- Alembic owns the schema.
- A one-shot `migrate` service runs `alembic upgrade head` before the API and
  worker start.
- Do not create tables ad hoc at API startup.
- Commit the initial migration and a test that upgrades an empty database.
- Use `DATABASE_URL` for the connection string. Default:
  `sqlite:////db/app.db`.

`simulate.py` uses `outputs/` as `[run].output_dir`. It copies inputs into

workflow bundle.

### 7.4 Security Rules for Paths

- Store only relative paths in the database.
- Validate that every path resolves inside the job root.
- Reject absolute paths, `..`, empty components, and symlinks.
- Never accept a path from a user for reads or writes.
- Use UUID-based upload directories; use only the basename of the original
  filename for display.
- Serve artifacts by artifact ID from the database, never by a query-string
  path.

## 8. Public API Contract

Base path: `/api/v1`. All endpoints except health require
`Authorization: Bearer <SERVICE_API_TOKEN>`.

### 8.1 Health and Capabilities

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/healthz` | Process is alive |
| `GET` | `/readyz` | DB reachable, migrations applied, data dirs writable |
| `GET` | `/api/v1/capabilities` | Integrators, barostats, defaults, limits, input formats |

`GET /capabilities` returns the frontend's source of truth for allowed values
and bounds. Do not hard-code a second copy in the frontend.

### 8.2 Files

| Method | Path | Purpose |
| --- | --- | --- |
| `POST` | `/api/v1/files` | Multipart upload; stream, hash, enforce size |
| `GET` | `/api/v1/files/{file_id}` | File metadata owned by caller |

Do not add file deletion in v1. Files are immutable and may be reused by
multiple jobs. Cleanup is an administrative maintenance task.

Upload response:

  "name": "complex.pdb",
  "size_bytes": 123456,
  "sha256": "...",
  "created_at": "2026-11-07T12:00:00Z"

### 8.3 Jobs

`GET /jobs/{id}` response shape:

```json
{
  "id": "...",
  "name": "7YAE test",
  "status": "running",
  "phase": "simulating",
  "current_stage": "equil-01",
  "progress": {
    "step": 12000,
    "total_steps": 100000,
    "percent": 12.0,
    "updated_at": "..."
  },
  "queue_position": null,
  "stages": [
    {
      "name": "equil-01",
      "kind": "equilibration",
      "status": "running",
      "steps_completed": 12000,
      "steps_target": 100000,
      "attempts": 1
    }
  ],
  "error": null,
  "created_at": "...",
  "updated_at": "..."

```

`queue_position` is `null` unless the status is `queued`; otherwise it is the
number of earlier queued jobs plus one.

### 8.4 Retry

Request:

```json
{
  "mode": "restart_stage",
  "stage": "equil-02"
}
```

Allowed modes:

| Mode | Meaning | `simulate.py` flag |
| --- | --- | --- |
| `resume` | Continue from checkpoints | none |
| `restart` | Rerun all simulation stages | `--restart` |
| `restart_stage` | Rerun one stage and later ones | `--restart-stage NAME` |
| `reparameterize` | Rebuild prepared system and clear stages | `--reparameterize` |

Rules:

- `resume` is allowed for `failed` and `canceled`, not `completed`.
- `restart`, `restart_stage`, and `reparameterize` are allowed for terminal
  jobs.
- `stage` must be one of the job's generated stage names.
- Retry does not change the job's spec. Changing settings requires a new job in
  v1.
- A retry resets `cancel_requested`, lease, worker, and run token, and sets
  status to `queued`.
- Reset stage rows according to the mode:
  - `resume`: leave completed stages completed; reset failed/canceled stages to
    pending.
  - `restart`: all stages pending.
  - `restart_stage`: target and later stages pending; earlier completed stages
    stay completed.
  - `reparameterize`: all stages pending.

### 8.5 Errors

Use a consistent error body:

```json
{
  "error": {
    "code": "invalid_stage",
    "message": "Stage 'foo' does not exist",
    "details": {"available": ["minimization", "equil-01"]}
  }
}
```

Status codes:

- `400` malformed request.
- `401` missing/invalid token.
- `404` unknown file/job/artifact.
- `409` invalid state transition.
- `413` upload too large.
- `422` schema validation failure.
- `429` queue or rate limit.
- `500` internal error.

## 9. Internal API Contract

Base path: `/internal/v1`. Require `X-Worker-Token: <WORKER_TOKEN>`. These
endpoints must not be exposed through the public reverse proxy.

| Method | Path | Purpose |
| --- | --- | --- |
| `POST` | `/workers/heartbeat` | Register/update worker, return cancel flag |
| `POST` | `/jobs/claim` | Atomically claim the oldest queued job |
| `POST` | `/jobs/{job_id}/progress` | Update phase, stage, step, percent |
| `POST` | `/jobs/{job_id}/stage` | Update one stage row |
| `POST` | `/jobs/{job_id}/finish` | Complete, fail, or cancel; register artifacts |

### 9.1 Worker Heartbeat

Request:

```json
{
  "worker_id": "gpu-0",
  "hostname": "md-gpu-1",
  "gpu_name": "NVIDIA ...",
  "gpu_uuid": "...",
  "version": "0.1.0",
  "status": "online",
  "current_job_id": "job_...",
  "run_token": "..."
}
```

Response:

```json
{
  "cancel_requested": false,
  "lease_expires_at": "2026-11-07T12:00:60Z"
}
```

If `current_job_id` and `run_token` match, heartbeat extends the lease. If they
do not match, do not extend the lease; the worker is stale.

### 9.2 Claim

Request:

```json
{
  "worker_id": "gpu-0",
  "gpu_uuid": "..."
}
```

Response `200`:

```json
{
  "job_id": "...",
  "run_token": "...",
  "config_path": "/data/jobs/.../config.toml",
  "job_root": "/data/jobs/...",
  "restart_mode": "resume",
  "restart_stage": null,
  "stages": [
    {"name": "minimization", "kind": "minimization", "steps_target": 0},
    {"name": "equil-01", "kind": "equilibration", "steps_target": 10000}
  ]
}
```

Response `204` when the queue is empty.

Claim must atomically:

1. select the oldest `queued` job;
2. set `status = claimed`;
3. set `worker_id`, new `run_token`, `lease_expires_at`, `attempt += 1`;
4. clear previous progress/error fields as appropriate;
5. append a `claimed` event;
6. commit.

Use `BEGIN IMMEDIATE` for SQLite. If multiple API threads call claim, they must
serialize.

### 9.3 Progress

Request:

```json
{
  "run_token": "...",
  "phase": "simulating",
  "stage": "equil-01",
  "step": 12000,
  "total_steps": 100000,
  "percent": 12.0,
  "updated_at": "2026-11-07T12:03:00Z"
}
```

API verifies `job.worker_id` and `job.run_token`. Stale tokens receive `409`.
Update job progress fields and `current_stage`; extend the lease. Do not append
an event for every progress call. Return `{ "cancel_requested": bool }`.

### 9.4 Stage

Request:

```json
{
  "run_token": "...",
  "name": "equil-01",
  "status": "completed",
  "steps_completed": 100000,
  "attempts": 1,
  "error": null
}
```

The stage must belong to the job. Update status, steps, timestamps, and
`manifest_json` if provided. Append a stage event only on status changes.

### 9.5 Finish

Request:

```json
{
  "run_token": "...",
  "status": "completed",
  "exit_code": 0,
  "error_code": null,
  "error_message": null,
  "artifacts": [
    {
      "stage_name": "production",
      "kind": "trajectory",
      "relative_path": "outputs/stages/production/trajectory.dcd",

```

Allowed `status`: `completed`, `failed`, `canceled`. API:

- verifies run token;
- validates every artifact path is inside the job root and exists;
- inserts artifact metadata;
- sets terminal status and timestamps;
- clears lease/worker/run token;
- appends a terminal event.

Artifact validation must reject absolute paths, `..`, symlinks, and files

## 10. Job State Machine

```text
queued
  │ claim
  ▼
claimed
  │ worker starts process
  ▼
running ──────────────┐
  │                   │ cancel requested
  │ complete          ▼
  ▼                canceling
completed              │ worker acknowledges
                       ▼
                    canceled

claimed/running -> failed  (worker error, lease lost)
failed/canceled/completed -> queued  (retry)
```

Statuses:

- `queued` — waiting for a worker.
- `claimed` — assigned to a worker; preparing to run.
- `running` — subprocess is active.
- `canceling` — cancellation requested; waiting for worker.
- `completed` — workflow exit code 0.
- `failed` — error or lost worker.
- `canceled` — cancellation completed.

Phase values on `jobs.phase`:

- `parameterizing`
- `minimizing`
- `simulating`
- `finalizing`

### 10.1 Lease and Worker Loss

- Worker heartbeat every 5–10 seconds; lease is 60 seconds.
- API reaper runs every 10 seconds in a background task.
- If a job in `claimed`, `running`, or `canceling` has an expired lease:
  - if `cancel_requested`, set `canceled`;
  - otherwise set `failed` with `error_code = "worker_lost"`.
- Do **not** automatically requeue a potentially live job. A requeue could run
  concurrently with a partitioned worker and corrupt the same workspace. Mark
  it failed and let the user retry.
- A stale worker's progress/finish calls are rejected by `run_token`.
- The worker on startup should log any local workspace it finds but must not
  assume ownership; the API is authoritative.

### 10.2 Cancellation

- Queued job: API immediately marks `canceled`; no worker is involved.
- Claimed/running job: API sets `cancel_requested = 1` and `status = canceling`.
- Worker heartbeat/progress returns `cancel_requested = true`.
- Worker sends `SIGINT` to the process group, waits 30 seconds, sends
  `SIGTERM`, waits 10 seconds, then `SIGKILL`.
- `simulate.py` already catches `KeyboardInterrupt` and preserves checkpoints.
- Worker reports `canceled` once the process exits.
- If the worker itself dies, the reaper marks the job canceled if the request
  was set; otherwise failed.

Important: start the subprocess in a new session (`start_new_session=True`) and
signal the whole process group. `simulate.py` starts `prepare_system.py` as a
child; signaling only the parent can leave the parameterizer running.

## 11. Job Creation Flow

`POST /api/v1/jobs` is synchronous for validation and workspace preparation.

1. Authenticate and validate the request with Pydantic (`extra="forbid"`).
2. Enforce limits from `policies.py`.
3. Verify all referenced file IDs exist and belong to the caller.
4. Generate `job_id` and create a temporary workspace.
5. Copy/hardlink inputs into `inputs/`.
   - For `pdb_id`, download from
     `https://files.rcsb.org/download/<ID>.pdb` only if
     `ALLOW_PDB_DOWNLOAD=true`. Validate the ID as four alphanumeric
     characters. Enforce the download size limit. Store it as a normal input
     file so the worker does not need network access.
6. Build the canonical `JobSpec`.
7. Generate `config.toml` from the spec and the absolute input paths.
8. Validate the generated TOML with `config.load_config()`.
9. Write `job.json`.
10. Atomically rename the temporary workspace to
    `/data/jobs/<job_id>/`.
11. In one DB transaction:
    - insert `jobs`;
    - insert `job_stages`;
    - insert the `created`/`queued` events.
12. Return `202` with the job.

If the API crashes between workspace creation and DB insert, the workspace is
orphaned. Add an admin cleanup task later. Do not leave a queued job without a
workspace.

## 14. Worker Design

### 14.1 Worker Loop

```text
register / heartbeat
while true:
  if current job:
    poll progress file
    send progress when changed
    send stage transitions
    check cancel flag via heartbeat
    if process exited:
      reconcile stage manifests
      send finish
      clear current job
  else:
    claim a job
    if claimed:
      mark running, launch subprocess
    else:
      sleep 2s
```

### 14.2 Job Launch

The worker builds a fixed command; it never accepts arbitrary flags or
executables:

```text
python /app/simulate.py --config <job_root>/config.toml --progress-file <job_root>/progress.json
```

Use `sys.executable` or the image's `python`. Add exactly one restart flag based
on the claim response:

- `resume`: none
- `restart`: `--restart`
- `restart_stage`: `--restart-stage <name>`
- `reparameterize`: `--reparameterize`

Set:

- `cwd=/app`
- `PYTHONUNBUFFERED=1`
- `CUDA_VISIBLE_DEVICES` from worker env
- `start_new_session=True`

Capture stdout/stderr to `logs/simulate.stdout` and `logs/simulate.stderr`.
Write worker logs to `logs/worker.log`.

### 14.3 Progress Polling

- Poll `progress.json` every 2 seconds.
- Send a progress update only when `(phase, stage, status, step)` changes or at
  least every 30 seconds.
- Heartbeat every 5–10 seconds even when no progress changes; this returns the
  cancel flag and extends the lease.
- Read `progress.json` atomically; `simulate.py` writes via temp file + replace.

### 14.4 Stage Reconciliation

At process exit, read every `outputs/stages/*/stage.json` and update the API's
stage rows. This is the authoritative completion record. Also read
`outputs/stages/minimization/stage.json` if minimization is enabled.

If the process exits 0 but a stage manifest is missing or not completed, report
failure rather than completed.

### 14.5 Exit Handling

- Exit code `0`: completed.
- Exit code `130` or a signal termination while `cancel_requested` is true:
  canceled.
- Any other code: failed; include the last stderr lines and the current stage.
- If cancellation was requested but the process exits nonzero, report canceled
  and preserve checkpoints.

### 14.6 Worker Image

The worker image should include only the worker Python code on top of the
existing OpenMM image. It needs `requests` (already in the simulation image) and
the standard library. It does not need SQLAlchemy, FastAPI, or database access.

## 15. Simulation Core Changes

These are small, testable changes to the existing workflow.

### 15.1 `--progress-file`

Add to `simulate.py`:

```text
--progress-file PATH
```

- `argparse` path, optional.
- Pass it into `run_workflow`.
- Do not write it during `--dry-run`.
- Do not let API users set it; the worker passes a fixed path.

### 15.2 Progress JSON

Use atomic writes (temporary file + `replace`). Suggested schema:

```json
{
  "phase": "simulating",
  "status": "running",
  "stage": "equil-01",
  "kind": "equilibration",
  "step": 12000,
  "total_steps": 100000,
  "percent": 12.0,
  "attempt": 1,
  "updated_at": "2026-11-07T12:03:00Z",
  "error": null
}
```

Phases:

- `starting`
- `parameterizing`
- `minimizing`
- `simulating`
- `completed`
- `failed`
- `canceled`

Write progress:

- before parameterization;
- after parameterization;
- before/after minimization;
- at stage start;
- periodically during a stage;
- at stage completion/failure;
- at workflow completion;
- on `KeyboardInterrupt` and on handled errors.

`stage.json` remains the authoritative per-stage record. The progress file is
for live monitoring.

### 15.3 Stage Progress Without a Custom OpenMM Reporter

The simplest implementation is to step in chunks and write progress between
chunks:

```python
interval = min(1000, max(100, stage.report_interval))
while simulation.currentStep < stage.steps:
    end = min(stage.steps, simulation.currentStep + interval)
    simulation.step(end - simulation.currentStep)
    write_progress(...)
```

This preserves OpenMM reporters and checkpoint intervals. OpenMM will still
invoke `StateDataReporter` and `CheckpointReporter` at their configured steps.
Choose the chunk size so a pathological `report_interval = 1` does not cause a
JSON write every step.

Alternative: implement a custom OpenMM reporter. The chunked approach is easier
to test and avoids depending on reporter internals.

### 15.4 Signal Handling

`simulate.py` already catches `KeyboardInterrupt` and returns 130. Add a
SIGTERM handler that raises `KeyboardInterrupt` (or sets a cancellation flag and
lets the main thread finish the current step), so the worker can escalate from
SIGINT to SIGTERM without leaving checkpoints unflushed.

Do not catch `KeyboardInterrupt` inside `run_stage` in a way that swallows the
cancellation. Let it propagate to `main`, which prints the checkpoint-preserved
message and exits 130.

### 15.5 Tests

Add tests for:

- progress file created at parameterization/minimization/stage boundaries;
- progress step/percent monotonic within a stage;
- progress file ends at `completed` on success;
- progress file reports `failed` on an induced error;
- SIGINT/SIGTERM produces exit 130 and leaves the stage checkpoint;
- chunked stepping does not change final step count or stage manifest.

  - `LocalStorage` in v1;
  - `S3Storage`/`GCSStorage` later.
- Keep the worker protocol transport-independent; it can later use Postgres
  `FOR UPDATE SKIP LOCKED` or a real queue.

### 21.1 SQLite to Postgres

1. Create the Postgres schema with Alembic.
2. Export/import rows with `pgloader` or a small Python script.
3. Copy `/data/jobs` to the new storage (or object storage).
4. Change `DATABASE_URL`.
5. Start one API instance, verify, then scale.
6. Keep the SQLite backup until verified.

When to move:

- more than one API instance;
- API and worker on different machines with a shared queue;
- API moved to Cloud Run;
- write contention from many workers/updates;
- need for managed backups/high availability.

### 21.2 Multiple GPU Workers

- Run one worker container per GPU.
- Set unique `WORKER_ID` and `CUDA_VISIBLE_DEVICES`.
- Keep one API process and SQLite if still on one host.
- `claim` already serializes `queued -> claimed`.
- Move to Postgres before running multiple API instances.

### 21.3 Object Storage

- Uploads/artifacts can move to GCS/S3.
- Worker still needs local scratch for OpenMM output; upload artifacts at
  finish, or keep a local cache.
- Use signed URLs for downloads when artifacts are in object storage.

## 22. Google Cloud Notes

For v1 on GCP:

- One Compute Engine GPU VM (for example, an NVIDIA T4/L4/A100 machine type).
- Attach a separate persistent disk; mount it at `/mnt/disks/md-data` and bind
  mount `/srv/md-service` from it. Do not put SQLite on the boot disk only.
- Docker Compose with the same API/worker/migrate layout.
- Expose only 443 at the firewall; SSH via IAP.
- Snapshot the persistent disk; use Litestream to GCS for database backups.
- Stop the GPU VM when idle to control cost; queued jobs remain in SQLite.
- Do not run SQLite on Cloud Run or GCSFuse. If the API moves to Cloud Run,
  move to Cloud SQL Postgres and GCS artifacts.
- Keep the GPU worker on Compute Engine; Cloud Run is not suitable for a
  long-running GPU simulation with local checkpoints.

## 24. Definition of Done

- A user can upload an input, create a job, and see it queue.
- The worker claims and runs the job with the existing CLI workflow.
- The API exposes phase, stage, step, percent, and queue position.
- A running job can be canceled; checkpoints remain and a retry resumes.
- Failed jobs can be retried with resume/restart/restart-stage/reparameterize.
- Artifacts, logs, and generated config are downloadable by ID.
- SQLite data and job files survive API/worker container recreation.
- All unsafe fields are rejected; no user path or executable reaches the
  workflow.
- Existing simulation tests pass on host and in Docker.
- Service tests cover auth, validation, queue transitions, cancellation, lease
  expiry, retry, and artifact path safety.
- Backup and restore are documented and tested.
- The architecture remains compatible with a later Postgres/object-storage
  migration.

## 25. Open Decisions

Resolve these before or during Phase 0. The defaults above are safe to start.

| Decision | Default | Change if |
| --- | --- | --- |
| Public or trusted | Trusted/internal | Public multi-tenant requires OIDC/API keys and stronger quotas |
| Auth | Static bearer token | Multiple users or public access |
| Hosting | Current server | GCP GPU VM if current hardware is insufficient |
| GPU count | One worker | Add one worker service per GPU |
| Artifact storage | Local disk | Use GCS/S3 when remote access or scale requires it |
| Trajectory visualization | Download only | Add a viewer or object storage + range requests later |
| PDB download | Enabled with env gate | Disable if the API should have no external network |
| Parameterization knobs | Limited subset | Expand only with explicit allowlists and tests |
| Production stage | Optional | Keep required if every job must have production |
| Retention | Keep all | Add cleanup when disk usage becomes a problem |
